# Approval visibility

Approvals and pairing consent are translated into English, German, Spanish, Russian and Simplified Chinese in language slice 6. The existing signing, connection, error and progress paths retain their behavior. The translated hint explains the visibility requirement and is announced through a status region and the disabled action's accessible description.

The dialog keeps its 90dvh cap and scrolls vertically. The details region retains up to 128 CSS pixels of minimum height (shorter content keeps its original fitted height). When the header, details minimum and footer exceed the cap, the outer dialog scrolls. Identity text wraps, and the header can wrap its columns at narrow or zoomed widths. The full name and URL remain reachable.

Review blocks and their descendants allow wrapping anywhere and shrink within their available width, including unbroken tokens and hex. Top-level typed-data fields retain the base grid. Recursive compound rows at depths 0 and 1 retain the base elements, classes, grid/flex layout and short labels. Only rows from depth 2 onward stack and show full paths, such as `order.items[3].to`. Indentation stops after two recursive levels. Paths use validated field names and array indices and wrap within the available column. At CSS viewport widths up to 240 pixels, reduced card padding and grid gaps leave room for complete glyphs in the shallow columns. Review content requires only vertical scrolling.

`reviewVisibility.ts` observes invisible, noninteractive rectangles covering each required block in slices of at most 16 vertical CSS pixels. This covers the middle of a long body as well as its ends. Every target is at least 1 pixel tall. The IntersectionObserver uses the viewport root (`root: null`), so the dialog, details region and nested message/calldata scrollers all clip intersections. Credit requires `isIntersecting`, exactly full intersection and positive target dimensions. The dialog and details region must also have positive dimensions. Scroll offsets never grant credit.

Coverage is remembered per block and its value. DOM structure/text changes, raw transaction field changes, typed values or type definitions, and exact fee quote changes invalidate that block. New blocks start unseen. Every distinct request object gets a monotonically increasing review generation from a WeakMap, independent of its ID and content. That generation keys the entire dialog component and its coverage controller/state. Closing unmounts the review. Staging consent creates a fresh object even when its URI is unchanged, and uses the same generation mechanism. PIN edits, unrelated store updates and completed blocks' safe layout changes preserve coverage. Mutation and resize observers reconcile browser changes; layout effects reconcile React commits before paint. Action handlers check coverage synchronously, and approval also compares the live request with its rendered content to reject a same-tick change before React commits. Consent waits for the URI's relay preview. Missing observer support leaves the action disabled.

Horizontal overflow fails closed even for a previously completed block. A block receives no observation targets while it or any descendant has `scrollWidth > clientWidth`, its horizontal bounds are clipped, or a descendant extends beyond the block's visible horizontal bounds. Those bounds include clipping ancestors and the viewport. Resize observations include descendants; viewport resize, content mutations and relevant attribute changes also recheck geometry. Repairing overflow creates fresh targets and requires fresh observations. Queued entries from the old targets grant no credit. Generated targets are bounded to the current block width so they cannot introduce horizontal overflow during resize.

Required blocks include identity, review rows, the complete primary message (decoded text or binary hex), typed domain/message values, amounts, fees and warnings. The existing optional digest and duplicate raw/canonical disclosures retain their behavior. The gate covers the complete primary representation without requiring those duplicate disclosures to be opened.

Typed-data domains with a chain ID wait for the wallet's asynchronous network check before approval. While it is pending, the review shows "Checking the network...". A failed check shows a required review block explaining that the wallet could not check its network and offers Retry; approval remains disabled until a check succeeds. A successful mismatch adds the existing warning as a required block, so the warning must be seen before approval. Matching chains preserve the existing completed review. Domains without a chain ID keep their existing behavior. The same renderer gate applies on desktop, which also retains its main-process confirmation. The check is bound to the review generation, domain chain ID, wallet network, provider and retry attempt; late results from earlier checks cannot satisfy a newer review. Click and PIN Enter share the guarded approval handler, and the action remains a non-submit button.

Messages containing only whitespace or Unicode default-ignorable characters show an explicit explanation and their complete raw signed bytes in hex as required content. Unsafe control and binary messages also retain their visible hex fallback. UTF-8 decoding preserves a leading byte order mark so it receives the same review treatment. An empty message shows "Empty message (0 bytes)." as a required block. Empty and collapsed-whitespace cards reuse their base vertical space with tighter padding; ordinary printable messages keep their existing rendering.

Account access displays the full active account address through `QrlAddress`, using the same text size as transaction addresses and compact vertical spacing. Switch-network reviews display one wallet-owned row, "Requested chain ID", containing only the validated `chainId` exactly as received, in monospace with left-to-right direction. Its label/value columns allow the maximum-length ID to wrap within the base fitted height. Ingress validation bounds it to a `0x`-prefixed hex string of at most 66 characters; the rendering guard enforces the same bounds. Extra switch fields, including names and RPC URLs, are never rendered. This store has no cached current chain ID, so the review omits the optional "Wallet chain ID" row and makes no new network request.

Add-network reviews render no request parameter values. Their gate covers the dApp identity and existing content, matching the base screen. The account address and requested switch ID add English copy to the base screen. Additional message copy labels invisible-only and empty content. All fitted cases retain their base dialog and region heights with these disclosures present. Approval outcomes remain unchanged: add-network declines with 4200, switch-network succeeds only for the wallet's current chain and otherwise declines with 4902, and desktop always declines switching with 4902.

## Evidence

`npm run smoke:approvals` serves the production build and uses headless Chromium with synthetic requests and local network replies. It exercises all seven approval methods and pairing consent, each with short and maximal fixtures, at 320 x 320, 360 x 320, 360 x 640, 390 x 844 and 1280 x 800. A temporary extension sets actual browser zoom to 200% at 360 x 640 and verifies the resulting 180 x 320 CSS viewport. The original 96 cases plus eighteen regression fixtures at all six layouts give 204 cases. It never signs or broadcasts.

Maximal fixtures use 128-character dApp names, 2048-character URLs, full 128-hex-digit addresses, a long printable message, 4096-byte calldata, a 66-character switch chain ID, and typed data with a 16 KiB string plus 256 array entries. Network fixtures also include ignored `chainName` and `rpcUrls` fields containing a bidi control and a 10 kB string. Every network case asserts the exact allowed review text, absence of the ignored fields from the dialog DOM, and monospace left-to-right switch IDs. The identity, string and array dimensions exercise their configured limits; message and transaction fixtures are bounded long-content cases.

The regression fixtures reuse the reviewer's ten-level `Nested0` through `Nested9` payload with its `SENSITIVE` leaf and whitespace messages `0x20`, `0x09`, `0x0a` and `0x200920`. They add a ten-level payload with a 2,000-character unbroken leaf, separate 2,000-character message and typed-data tokens, a message containing only U+200B and U+202E, and the ingress-valid empty message `0x`. Every regression requires an observable primary representation, full block coverage and a successful transition to the existing PIN check after review. The shallow grid retains its base column width. Independent character-range assertions check every glyph inside the resulting deep column at all six layouts. They assert the deepest value's label is `value.value.value.value.value.value.value.value.value.value` and track every path character through all clipping ancestors. At 320 pixels the path must wrap onto multiple lines, remain horizontally unclipped and reach full character visibility before approval.

The probe independently measures descendant and text-line rectangles, checks scroll widths and horizontal scroll offsets, tracks real intersections, scrolls each unseen slice into view, checks controls for clipping and overlapping elements, verifies both scrolling modes, and asserts that the action stays disabled until coverage completes. Regression cases additionally track each painted primary character through all clipping ancestors, proving that the complete visible representation was seen before approval. Signed whitespace is measured through its hex digits; collapsible spaces in the empty-message label are excluded from glyph counts. It also changes a reviewed message, identity, typed-data chain warning and requested switch ID, and checks empty-message, empty-account and missing-network-parameter reviews. Three horizontal-overflow controls invalidate completed reviews through descendant scrolling, a displaced descendant and a viewport resize; approval stays blocked during overflow and recovers after a fresh review. Eight forced-zero-height controls must remain disabled. Separate zero-height targets reproduce Chromium's fully-intersecting zero-area report during those controls.

Eighteen additional chain-check cases hold the RPC reply at all six layouts, then return a matching chain, a mismatching chain, or a failure followed by a successful retry with a mismatch. They read every current block while the read is pending or failed and assert that click, PIN Enter and submit cannot proceed. Late mismatch warnings start offscreen and require fresh visibility before approval can reach the existing PIN check. `results.json` records these cases under `chainChecks`; screenshots cover the pending and failed states. Unit tests repeat the chain-check cases for web and desktop, including domains without a chain ID, chain ID zero and late success/failure after an identical request object is replaced.

The probe stays local because the maximal cases require substantial scrolling. `APPROVAL_ARTIFACTS` selects the evidence directory (default: the system temporary directory's `approval-visibility` folder). `results.json` records the duration, dimensions, scrolling modes, block and character coverage, network content checks, changes, queued-request reproductions and negative controls. `parity.json` records initial dialog height, region height, action state and fit for every fixture at 1280 x 800 and 390 x 844. The 44 fixtures include all regular, maximal, adversarial, queued, changed-content and empty cases, giving 88 measurements. Closed optional disclosures are excluded from fit calculations; clipping and scrolling both mean the base did not fit. In particular, a base mobile header with a truncated URL needs wrapping to show its full identity. `APPROVAL_PARITY_ONLY=1` selects this matrix. The default comparison uses `scripts/approval-parity-baseline.json`, captured from unchanged `origin/dev` at `0aa0559ea90b36f47bc72f338b09e42f91b6733c`. It enforces exact dialog/region heights and immediate action availability for all 45 fully fitted base cases, with no exceptions. `APPROVAL_PARITY_BASE` can supply a freshly measured baseline JSON. `APPROVAL_PORT` allows separate baseline and branch servers. Regression and failure screenshots are saved there. `APPROVAL_CASE` selects a diagnostic subset.

Seven English copy/control snapshots were generated from an untouched archive of `fadf59e`, whose production files match `origin/dev` at `b1785b8`. Additional snapshots cover the restored add-network screen, account address and requested switch ID. Mock observers settle before those captures, so fitted actions are enabled. Browser bounds from the same archive additionally compare the four signing screens, consent and add-network: `APPROVAL_BASELINE=1` captures the base, and `APPROVAL_BASE_BOUNDS` points to its `english-base-bounds.json` when running the changed build. The comparison checks exact text, painted text-range bounds and control bounds/states for six screens. The account and switch additions are listed explicitly above.

jsdom tests mock geometry and IntersectionObserver and prove the gate's state machine, value invalidation, stale callbacks, click/keyboard/submit guards and dismissal. They cover block and descendant scroll overflow, descendants extending left or right, descendant resize and content mutation, synchronous approval guards, and fresh coverage after overflow repair. Message tests cover required hex for whitespace and invisible characters, including a leading byte order mark, and the visible empty representation. Typed-data tests distinguish a five-level nested `to` from a top-level `to`, cover full paths through records and multidimensional arrays, and preserve shallow labels and the ten-level leaf's bounded indentation. Ingress tests accept all ten regression cases and compute typed-data digests. Network tests also verify as-received switch IDs, ignored names and RPC URLs with bidi controls and a 10 kB string, omission of invalid IDs, unchanged approval outcomes, and fresh visibility after an ID change. The headless browser probe supplies the evidence for real visibility. These renderer checks do not qualify physical devices or native confirmation windows.

## Identity and equality audit

Request identity is an object-to-generation mapping, independent of string encodings. `reviewGeneration` checks counter exhaustion before assigning another safe integer. The approval action also compares the captured request object with the current store object before checking coverage or PIN state. Consent actions compare their generation and exact URI; an earlier asynchronous handshake can only clear its own consent object.

`reviewValueKey` encodes each node as a JSON array with an explicit type tag. Strings keep JSON escaping and boundaries. Arrays keep length, item boundaries and holes; objects keep ordered key/value entries. Undefined, null, empty strings, absent keys, numbers, numeric strings and bigint are distinct. A bigint tag cannot collide with a user object shaped like an old bigint replacer. Unsupported non-JSON objects fail closed. Equality is conservative about object entry order.

| Location | Identity/equality source | Collision argument |
| --- | --- | --- |
| Approval and consent component keys; visibility state/controller; dismissal timing | Numeric review generation | Unique per request object; reused string IDs, numeric versus string IDs, and identical contents cannot share a mounted review. |
| `reviewContentKey` action snapshot | `reviewValueKey` of session, typed ID, method, params, metadata, account and chain | Typed JSON tree preserves every field boundary and missing value; live object identity is checked separately. |
| Transaction fee preview `requestKey` | `reviewValueKey([generation, transactionParams])` | Generation and structured params are separate array entries. No separator interpolation or ID coercion. |
| Typed-data chain check | `reviewValueKey([generation, blockchain, domainChainId, attempt])` and provider identity | Pending, failed and ready results belong to one review and network check; replaced requests and cancelled reads cannot supply a newer review's chain ID. |
| Exact fee block | `reviewValueKey(approvedFee)` | Gas limit and all quote fields, including bigint, retain types and boundaries. |
| Transaction from/to/value/gas blocks | `reviewValueKey` of the raw field | Formatted amounts and gas values cannot hide changes in raw types, values or absence. |
| Typed domain/message blocks | `reviewValueKey([field, types, value])` | Includes field name/type, the complete type definitions and recursively typed value. Nested record and array boundaries remain distinct. |
| Message raw-byte attribute | One exact hex string | No composition or coercion; the enclosing DOM version distinguishes an absent attribute from an empty one. |
| Coverage block version | JSON of a recursive DOM tree | Node types, element names, individual text nodes, review attributes and ordered children remain separate. Observation tiles are excluded. `textContent` flattening is never used for equality. |
| Typed React list keys | Raw unique field names or integer array positions within their own sibling lists | Validated typed schemas reject duplicate names. Object entries and array positions are unique within their lists. Semantic coverage is separately checked above. |
| Consent URI preview/action comparisons | Exact single URI string plus generation | Full-string equality has no composition ambiguity; a repeated URI still has its own generation. |

Full path strings, formatted error paths and canonical JSON disclosures are display text. They grant no identity or equality credit. Validated typed-data identifiers contain neither dots nor brackets, so the displayed field/index paths are also unambiguous. Address rendering uses numeric group positions as React list keys; block coverage uses the DOM tree and exact raw address. Geometry style comparisons interpolate only bounded numeric measurements and constant CSS units, and carry no approved values.

The round 2 queue reproduction uses real store promotion: numeric ID `1` followed by string ID `"1"`, with nested `{a:1,b:23}` and `{a1b:23}` after a long common prefix. It reads and rejects the first, confirms the second's changed field is below the visible region, verifies that every old tile was removed and approval cannot reach PIN, then reads the second and reaches PIN. A distinct-ID control runs at both requested viewports. Unit tests also cover same-tick equal-content object replacement, repeated IDs after dismissal, in-place subtree edits, arrays `["ab"]` versus `["a","b"]`, empty versus missing values, numbers versus numeric strings, and bigint/object ambiguities.

## Slice 6 language matrix

The language runner repeats the entire matrix described above in all five languages, including the collapsed, overflow, queued-request and delayed-chain controls. Language-specific selectors use catalog labels while fixture names, URLs, messages, typed-data paths/values, chain IDs, addresses and raw bytes remain unchanged. Empty-message glyph tracking uses the translated zero-byte explanation. The default command verifies 1,020 main cases, 90 delayed-chain cases, 40 collapsed controls, 15 overflow controls, 20 queued requests, 20 changed-content checks and 20 empty-content checks, with 440 initial geometry measurements. It asserts each language's counts before accepting the aggregate result. A separate observer starts at dialog mount and records full intersections using the geometry from each observation; current geometry and glyph visibility are checked again at scroll destinations. This captures valid frames before a satisfied hint disappears and avoids comparing observations against a later layout. Every-frame monitoring rejects enabled actions with unseen tiles.

Each language writes its own evidence folder under `APPROVAL_ARTIFACTS`; the aggregate `results.json` reports both per-language and total elapsed seconds. `APPROVAL_JOBS` selects one to five independent browser workers (default one), with distinct ports starting at `APPROVAL_PORT`. The matrix stays local. See [slice 6 translation evidence](I18N.md#slice-6-pairing-consent-and-dapp-approvals) for the pinned English oracle, text-bound comparison and language reviews. The gate and layout code are unchanged by the translation slice.

The complete local slice 6 run on 2026-10-23 passed all five languages in 608.55 seconds with five workers. Each language passed all 204 main cases and every control listed above. Detailed timings and gate exit codes are recorded in [the validation report](I18N.md#local-validation-2026-10-23).
