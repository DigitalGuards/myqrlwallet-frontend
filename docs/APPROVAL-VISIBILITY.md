# Approval visibility

Approvals and pairing consent remain English. The existing signing, connection, error and progress paths retain their behavior. The new hint explains the visibility requirement and is announced through a status region and the disabled action's accessible description.

The dialog keeps its 90dvh cap and scrolls vertically. The details region retains up to 128 CSS pixels of minimum height (shorter content keeps its original fitted height). When the header, details minimum and footer exceed the cap, the outer dialog scrolls. Identity text wraps, and the header can wrap its columns at narrow or zoomed widths. The full name and URL remain reachable.

Review blocks and their descendants allow wrapping anywhere and shrink within their available width, including unbroken tokens and hex. Compound typed-data fields stack their labels and values and use at most two levels of indentation. Further nesting keeps the same available width and labels every key and array index with its full path from the top-level field, such as `order.items[3].to`. These paths use the validated field names and array indices and wrap within the column. Top-level fields and the first two recursive levels retain their short labels. The ten-level regression fixture has a 186 CSS pixel leaf column at a 320 CSS pixel viewport. Review content requires only vertical scrolling.

`reviewVisibility.ts` observes invisible, noninteractive rectangles covering each required block in slices of at most 16 vertical CSS pixels. This covers the middle of a long body as well as its ends. Every target is at least 1 pixel tall. The IntersectionObserver uses the viewport root (`root: null`), so the dialog, details region and nested message/calldata scrollers all clip intersections. Credit requires `isIntersecting`, exactly full intersection and positive target dimensions. The dialog and details region must also have positive dimensions. Scroll offsets never grant credit.

Coverage is remembered per block and its value. Text changes, raw transaction amount changes and exact fee quote changes invalidate that block. New blocks start unseen, and request or consent-URI replacement starts a fresh review. PIN edits, unrelated store updates and completed blocks' safe layout changes preserve coverage. Mutation and resize observers reconcile browser changes; layout effects reconcile React commits before paint. Action handlers check coverage synchronously, and approval also compares the live request with its rendered content to reject a same-tick change before React commits. Consent waits for the URI's relay preview. Missing observer support leaves the action disabled.

Horizontal overflow fails closed even for a previously completed block. A block receives no observation targets while it or any descendant has `scrollWidth > clientWidth`, its horizontal bounds are clipped, or a descendant extends beyond the block's visible horizontal bounds. Those bounds include clipping ancestors and the viewport. Resize observations include descendants; viewport resize, content mutations and relevant attribute changes also recheck geometry. Repairing overflow creates fresh targets and requires fresh observations. Queued entries from the old targets grant no credit. Generated targets are bounded to the current block width so they cannot introduce horizontal overflow during resize.

Required blocks include identity, review rows, the complete primary message (decoded text or binary hex), typed domain/message values, amounts, fees and warnings. The existing optional digest and duplicate raw/canonical disclosures retain their behavior. The gate covers the complete primary representation without requiring those duplicate disclosures to be opened.

Messages containing only whitespace or Unicode default-ignorable characters show an explicit explanation and their complete raw signed bytes in hex as required content. Unsafe control and binary messages also retain their visible hex fallback. UTF-8 decoding preserves a leading byte order mark so it receives the same review treatment. An empty message shows "Empty message (0 bytes)." as a required block. Ordinary printable messages keep their existing rendering.

Account access displays the full active account address through `QrlAddress`. Switch-network reviews display one wallet-owned row, "Requested chain ID", containing only the validated `chainId` exactly as received, in monospace with left-to-right direction. Ingress validation bounds it to a `0x`-prefixed hex string of at most 66 characters; the rendering guard enforces the same bounds. Extra switch fields, including names and RPC URLs, are never rendered. This store has no cached current chain ID, so the review omits the optional "Wallet chain ID" row and makes no new network request.

Add-network reviews render no request parameter values. Their gate covers the dApp identity and existing content, matching the base screen. The account address and requested switch ID are the two explicit exceptions to the fitted English comparison. Additional message copy labels invisible-only and empty content. Approval outcomes remain unchanged: add-network declines with 4200, switch-network succeeds only for the wallet's current chain and otherwise declines with 4902, and desktop always declines switching with 4902.

## Evidence

`npm run smoke:approvals` serves the production build and uses headless Chromium with synthetic requests and local network replies. It exercises all seven approval methods and pairing consent, each with short and maximal fixtures, at 320 x 320, 360 x 320, 360 x 640, 390 x 844 and 1280 x 800. A temporary extension sets actual browser zoom to 200% at 360 x 640 and verifies the resulting 180 x 320 CSS viewport. The original 96 cases plus ten regression fixtures at all six layouts give 156 cases. It never signs or broadcasts.

Maximal fixtures use 128-character dApp names, 2048-character URLs, full 128-hex-digit addresses, a long printable message, 4096-byte calldata, a 66-character switch chain ID, and typed data with a 16 KiB string plus 256 array entries. Network fixtures also include ignored `chainName` and `rpcUrls` fields containing a bidi control and a 10 kB string. Every network case asserts the exact allowed review text, absence of the ignored fields from the dialog DOM, and monospace left-to-right switch IDs. The identity, string and array dimensions exercise their configured limits; message and transaction fixtures are bounded long-content cases.

The regression fixtures reuse the reviewer's ten-level `Nested0` through `Nested9` payload with its `SENSITIVE` leaf and whitespace messages `0x20`, `0x09`, `0x0a` and `0x200920`. They add a ten-level payload with a 2,000-character unbroken leaf, separate 2,000-character message and typed-data tokens, a message containing only U+200B and U+202E, and the ingress-valid empty message `0x`. Every regression requires an observable primary representation, full block coverage and a successful transition to the existing PIN check after review. The nested fixtures also require at least 120 CSS pixels of reading width at the 320-pixel viewport. They assert the deepest value's label is `value.value.value.value.value.value.value.value.value.value` and track every path character through all clipping ancestors. At 320 pixels the path must wrap onto multiple lines, remain horizontally unclipped and reach full character visibility before approval.

The probe independently measures descendant and text-line rectangles, checks scroll widths and horizontal scroll offsets, tracks real intersections, scrolls each unseen slice into view, checks controls for clipping and overlapping elements, verifies both scrolling modes, and asserts that the action stays disabled until coverage completes. Regression cases additionally track each painted primary character through all clipping ancestors, proving that the complete visible representation was seen before approval. Signed whitespace is measured through its hex digits; collapsible spaces in the empty-message label are excluded from glyph counts. It also changes a reviewed message, identity, typed-data chain warning and requested switch ID, and checks empty-message, empty-account and missing-network-parameter reviews. Three horizontal-overflow controls invalidate completed reviews through descendant scrolling, a displaced descendant and a viewport resize; approval stays blocked during overflow and recovers after a fresh review. Eight forced-zero-height controls must remain disabled. Separate zero-height targets reproduce Chromium's fully-intersecting zero-area report during those controls.

The probe stays local because the maximal cases require substantial scrolling. `APPROVAL_ARTIFACTS` selects the evidence directory (default: the system temporary directory's `approval-visibility` folder). `results.json` records the duration, dimensions, scrolling modes, block and character coverage, network content checks, changes and negative controls. Regression and failure screenshots are saved there. `APPROVAL_CASE` selects a diagnostic subset.

Seven English copy/control snapshots were generated from an untouched archive of `fadf59e`, whose production files match `origin/dev` at `b1785b8`. Additional snapshots cover the restored add-network screen, account address and requested switch ID. Mock observers settle before those captures, so fitted actions are enabled. Browser bounds from the same archive additionally compare the four signing screens, consent and add-network: `APPROVAL_BASELINE=1` captures the base, and `APPROVAL_BASE_BOUNDS` points to its `english-base-bounds.json` when running the changed build. The comparison checks exact text, painted text-range bounds and control bounds/states for six screens. The account and switch additions are listed explicitly above.

jsdom tests mock geometry and IntersectionObserver and prove the gate's state machine, value invalidation, stale callbacks, click/keyboard/submit guards and dismissal. They cover block and descendant scroll overflow, descendants extending left or right, descendant resize and content mutation, synchronous approval guards, and fresh coverage after overflow repair. Message tests cover required hex for whitespace and invisible characters, including a leading byte order mark, and the visible empty representation. Typed-data tests distinguish a five-level nested `to` from a top-level `to`, cover full paths through records and multidimensional arrays, and preserve shallow labels and the ten-level leaf's bounded indentation. Ingress tests accept all ten regression cases and compute typed-data digests. Network tests also verify as-received switch IDs, ignored names and RPC URLs with bidi controls and a 10 kB string, omission of invalid IDs, unchanged approval outcomes, and fresh visibility after an ID change. The headless browser probe supplies the evidence for real visibility. These renderer checks do not qualify physical devices or native confirmation windows.
